AWS
Identity Management
Identities in AWS are managed using AWS Identity and Access Management (IAM).
When working with AWS Organizations, customers have the option for central identity management for the entire AWS Organization using AWS IAM Identity Center — a single-sign-on (SSO) and federated identity 
management service (working with Microsoft Entra ID, Google Workspace, and more).
Since there might be a failure with a remote identity provider (IdP) or with AWS IAM Identity Center, AWS recommends creating two IAM users on the root of the AWS Organizations tree, and an IAM break-glass 
role on each of the accounts in the organization, to allow access in case of emergency.

Passwords for the break-glass IAM accounts must be stored in a secured vault, and once the work on the break-glass accounts is over, the passwords must be replaced immediately to avoid reuse.
Access using break-glass IAM accounts must be temporary


Auditing
All API calls within the AWS environment are logged into AWS CloudTrail by default, and stored for 90 days.
it is recommended to send all CloudTrail logs to a central S3 bucket, from the entire AWS Organization.
Since audit trail logs contain sensitive information, it is recommended to encrypt all data at rest using customer-managed encryption keys and limit access to the log files to the SOC team for investigation 
purposes.
Audit logs stored inside AWS CloudTrail can be investigated using Amazon GuardDuty.

creating RDS cluster:

- availability zones

- db_subnet_group_name : subnet group for the RDS
- vpc security group ids : [security group list for the cluster]
- backup retention period : how long to keep the backup snapshots
- preferred backup window : when to create the backup
- storage encrypted : true/false
- kms key id : reference to kms key for encrypt/decrypt
- deletion protection : prevent it from being deleted true/false
- master username
- manage master user password : true/false , manage the password and keep it encypted via aws_iam_policy
- database cluster parameter group id : create a RDS parameter group with key values relatd to the RDS specifications
- is it managed or serverless cluster?

creating RDS instance:
- rds identifier
- reference to rds cluster
- instance class : EC2 instance or Serverless
- engine and engine version (same as cluster)
- availability zone (only one in here)
- CA certificate identifier : reference to the certificate for SSL for the connection to DB
- performance insights: true/false
- auto minor version upgrade: true/false, for example from 12.4 to 12.8
- enhanced monitoring: 
    * monitoring interval: 15s or 30s or 1m,...
    * monitoring role arn : needs a role that allows enhanced monitoring

data "aws_iam_policy_document" "policy_no_roles" {

  # deny any connection that is not SSL / HTTPS
  statement {
    sid    = "DenyNonSSLConnections"
    effect = "Deny"
    actions = [
      "s3:*",
    ]

    principals {
      type        = "AWS"
      identifiers = ["*"]
    }

    resources = [
      "MY-BUCKET-ARN",
      "MY-BUCKET-ARN/*",
    ]

    condition {
      test     = "Bool"
      variable = "aws:SecureTransport"
      values = [
        "false",
      ]
    }
  }

  # deny any put in the S3 bucket that doesn't use the correct KMS encryption
  statement {
    sid    = "DenyIncorrectEncryptionKey"
    effect = "Deny"
    actions = [
      "s3:PutObject",
    ]

    principals {
      type        = "AWS"
      identifiers = ["*"]
    }
    resources = [
      "MY-BUCKET-ARN/*",
    ]
    condition {
      test     = "StringNotEquals"
      variable = "s3:x-amz-server-side-encryption-aws-kms-key-id"
      values = [
        var.kms_key_arn,
      ]
    }
  }

  # block public read ACL
  statement {
    sid    = "DenyPublicReadACL"
    effect = "Deny"
    actions = [
      "s3:PutObject",
      "s3:PutObjectAcl",
    ]

    principals {
      type        = "AWS"
      identifiers = ["*"]
    }

    resources = [
      "MY-BUCKET-ARN/*",
    ]

    condition {
      test     = "StringEquals"
      variable = "s3:x-amz-acl"
      values = [
        "public-read",
        "public-read-write",
        "authenticated-read",
      ]
    }
  }

  # block allowing public access to users for this bucket
  statement {
    sid    = "DenyPublicReadGrant"
    effect = "Deny"
    actions = [
      "s3:PutObject",
      "s3:PutObjectAcl",
    ]

    principals {
      type        = "AWS"
      identifiers = ["*"]
    }

    resources = [
      "MY-BUCKET-ARN/*",
    ]

    condition {
      test     = "StringLike"
      variable = "s3:x-amz-grant-read"
      values = [
        "*http://acs.amazonaws.com/groups/global/AllUsers*",
        "*http://acs.amazonaws.com/groups/global/AuthenticatedUsers*",
      ]
    }
  }


  statement {
    sid    = "DenyPublicBucketReadACL"
    effect = "Deny"
    actions = [
      "s3:PutBucketAcl",
    ]

    principals {
      type        = "AWS"
      identifiers = ["*"]
    }

    resources = [
      "MY-BUCKET-ARN"
    ]

    condition {
      test     = "StringEquals"
      variable = "s3:x-amz-acl"
      values = [
        "public-read",
        "public-read-write",
        "authenticated-read",
      ]
    }
  }

  # deny any connections to S3 bucket that is not coming from specific VPC endpoint or specific IP address
  statement {
    sid    = "DenyNonVPCEndpoint"
    effect = "Deny"
    actions = [
      "s3:*",
    ]

    principals {
      type        = "AWS"
      identifiers = ["*"]
    }

    resources = [
      "MY-BUCKET-ARN/*",
    ]

    condition {
      test     = "NotIpAddress"
      variable = "aws:SourceIp"
      values = [
        "159.53.0.0/16",
        "146.143.0.0/16",
        "170.148.0.0/16",
        "103.246.196.0/23",
      ]
    }

    condition {
      test     = "StringNotEquals"
      variable = "aws:sourceVpce"
      values   = var.vpc_endpoint_ids
    }
  }
}


** failover modes **

1. Active/Active failover => means both servers in different data centers are ready to take traffic at any moment (both connected to load balancer)
2. Active/Passive failover, hot-cold => the second server is turned off, but can be turned on and run again (we might have the pipeline to create the infra in the second region)
3. Active/Passive failover, hot-hot => similar to active-active, however second server will only take data when first one is down
4. Active/Passive failover, hot-warm => the second server is created, however it is not ready to take data immediately, needs to sync and then can be used



*** SCP examples ***

SCPs do not grant permissions to the IAM users and IAM roles in your organization. No permissions are granted by an SCP. An SCP defines a permission guardrail, 
or sets limits, on the actions that the IAM users and IAM roles in your organization can perform. To grant permissions, the administrator must attach policies to 
control access, such as identity-based policies that are attached to IAM users and IAM roles, and resource-based policies that are attached to the resources in your accounts.
