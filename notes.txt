How to drain an Kubernetes node: You can use "kubectl drain" to safely evict all of your pods from a node before you perform maintenance on the node (e.g. kernel upgrade, hardware maintenance, etc.). Kubernetes Disruption:
pods do not disappear until someone(person or controller) destroys them, or there is an unavoidable hardware or system software error.
we call these unavoidable cases "Involuntary Disruptions" to an application, examples:
- a hardware failure of the physical machine backing the node
- cluster admin deletes VM / instance by mistake
- cloud provider or hypervisor failure makes VM disappear
- kernel panic
- node disappear from cluster due to cluster network partition
- eviction of pod due to the node being out of resource

Voluntary Disruption:
actions initiated by application owner and those initiated by a cluster admin. 
application owner actions:
- deleting a deployment or other controller that manages the pod
- updating deployment's pod template causing a restart
- directly deleting a pod (acident)

cluster admin actions:
- draining a node for repair or upgrade
- draining a node from a cluster to scale the cluster down
- removing a pod from node to permit something else to fit in the node

Pod Disruption Budget

Kubernetes offers features to help you run highly available applications even when you introduce frequent voluntary disruptions.

As an application owner, you can create a PodDisruptionBudget (PDB) for each application. A PDB limits the number of Pods of a replicated application that are down simultaneously from voluntary disruptions. 
For example, a quorum-based application would like to ensure that the number of replicas running is never brought below the number needed for a quorum. A web front end might want to ensure that the number of 
replicas serving load never falls below a certain percentage of the total.

A PDB specifies the number of replicas that an application can tolerate having, relative to how many it is intended to have. For example, a Deployment which has a "".spec.replicas: 5" is supposed to have 5 
pods at any given time. If its PDB allows for there to be 4 at a time, then the Eviction API will allow voluntary disruption of one (but not two) pods at a time.

PodDisruptionBudget example
Consider a cluster with 3 nodes, node-1 through node-3. The cluster is running several applications. One of them has 3 replicas initially called pod-a, pod-b, and pod-c. Another, unrelated pod without a PDB, 
called pod-x, is also shown. Initially, the pods are laid out as follows:

node-1	            node-2	          node-3
pod-a available	    pod-b available	  pod-c available
pod-x available		

All 3 pods are part of a deployment, and they collectively have a PDB which requires there be at least 2 of the 3 pods to be available at all times.

For example, assume the cluster administrator wants to reboot into a new kernel version to fix a bug in the kernel. The cluster administrator first tries to drain node-1 using the kubectl drain command. 
That tool tries to evict pod-a and pod-x. This succeeds immediately. Both pods go into the terminating state at the same time. This puts the cluster in this state:

node-1 draining	     node-2	              node-3
pod-a terminating	   pod-b   available	  pod-c available
pod-x terminating		

The deployment notices that one of the pods is terminating, so it creates a replacement called pod-d. Since node-1 is cordoned, it lands on another node. Something has also created pod-y as a replacement for 
pod-x.

(Note: for a StatefulSet, pod-a, which would be called something like pod-0, would need to terminate completely before its replacement, which is also called pod-0 but has a different UID, could be created. 
Otherwise, the example applies to a StatefulSet as well.)

Now the cluster is in this state:

node-1 draining	    node-2	          node-3
pod-a terminating	  pod-b available	  pod-c available
pod-x terminating	  pod-d starting	  pod-y

At some point, the pods terminate, and the cluster looks like this:

node-1 drained	      node-2	            node-3
                      pod-b available	    pod-c available
                      pod-d starting	    pod-y

At this point, if an impatient cluster administrator tries to drain "node-2" or "node-3", the drain command will block, because there are only 2 available pods for the deployment, and its PDB 
requires at least 2. After some time passes, "pod-d" becomes available.

lsof command
The lsof command is an acronym for "list open files," but its potential isn't limited to just that role. It's commonly said that in Linux, everything is a file. In many ways, that's true, so a utility 
that lists open files is actually pretty useful. The lsof utility is a robust interface for the information inside the /proc virtual filesystem.

what process is using a particular directory:
> lsof /run

what files a particular process has open:
> lsof -p 890

discover what files a particular user has open:
> lsof -u admin 
> lsof /proc/{user-id}/fd | wc - l
> lsof -u {user} | wc -l

Operator and CRD:

1. Operators make it possible to extend Kubernetes functionality to stateful applications as well, not just stateless applications. And that alone is an important advantage, because stateful cloud applications and services are much more complex to manage than stateless ones. Some stateful operators are: Prometheus Operator for the monitoring solution and Postgres Operator to manage high-availability PostgreSQL database clusters.
2. Operators standardize manual activities and create a common and consistent approach to automation.
3. Operators can be easily transported from one environment to another and from one project to another. This has enabled the emergence of an ecosystem with many more generic Operators that can be downloaded, configured, and used for different projects without the need to develop them in-house. Later, we will see which are the most popular hubs for finding generic

The Kubernetes project defines “Operator” in a simple way: “Operators are software extensions that use custom resources to manage applications and their components“. In other words, using Operators enables us 
to view an application as a single object that exposes only the adjustments that make sense for the application, instead of a collection of primitives (such as Pods, Deployments, Services, or ConfigMaps).
they are called “native Kubernetes applications“, and this definition can also be viewed in another, more operational way. K8s Operators are controllers for packaging, managing, and deploying applications 
on Kubernetes. In order to do these things, the Operator uses Custom Resources (CR) that define the desired configuration and state of a specific application through Custom Resource Definitions (CRD).
The Operator's role is to reconcile the actual state of the application with the state desired by the CRD using a control loop in which it can automatically scale, update, or restart the application. Practically speaking, Kubernetes offers basic commands, primitives, that can be used by Operators to define more complex actions.

An almost infinite number of things can be automated through an Operator, however some typical operations are more common than others.
* The ability to deploy an application on demand
* Making a backup of an application state or restarting an application from a given backup
* Managing the update of an application with all its dependencies including new configuration settings and necessary database changes
* Exposing a service to applications that do not support Kubernetes APIs.

Operators are typically implemented as custom controllers that extend the Kubernetes API with new resources, and provide custom logic for managing these resources. For example, a database operator might 
create a custom resource called Database that represents a database instance, and provide custom logic for creating and managing instances of this resource.

Operators are hard to create and are usually written in GO language, but we can use “Operator Framework“ or “Kubebuilder” to develop them easier.
List of existing operators: https://artifacthub.io/packages/search

1- To create a Kubernetes operator, you first define a custom resource definition (CRD) for the resource you want to manage. For example, you might define a CRD named SampleDB to represent a sample database 
instance.
2- Next, you write a custom controller that watches for instances of the SampleDB resource and performs actions based on changes to these resources. For example, the controller might deploy a database 
instance when a SampleDB resource is created, or take a backup of the database when the SampleDB resource is updated.
3- To deploy an operator, you first build the operator using the Operator SDK or another tool. Then you create a deployment in the cluster that runs the operator, and create an instance of the SampleDB 
resource using kubectl or another tool.
4- Once the operator is deployed and the SampleDB resource is created, the operator will begin to manage the resource. It will perform tasks such as deploying the database, taking backups, handling upgrades, 
and simulating failure.
How to deploy Prometheus Operator (without Helm): https://prometheus-operator.dev/docs/user-guides/getting-started/


Break Glass

Using modern cloud environments, specifically production environments, decreases the need for human access.
It makes sense for developers to have access to Dev or Test environments, but in a properly designed production environment, everything should be automated — from deployment, and observability to self-healing. 
In most cases, no human access is required.
Production environments serve customers, require zero downtime, and in most cases contain customers data.
There are cases such as emergency scenarios where human access is required.

In mature organizations, this type of access is done by the Site reliability engineering (SRE) team.
The term break-glass is an analogy to breaking a glass to pull a fire alarm, which is supposed to happen only in case of emergency.

break-glass accounts should be used in emergency cases only.

* 	Authentication — All access through the break-glass mechanism must be authenticated, preferred against a central identity provider, and not using local accounts
* 	Authorization — All access must be authorized using role-based access control (RBAC), following the principle of least privilege
* 	MFA — Since most break-glass scenarios require highly privileged access, it is recommended to enforce multi-factor authentication (MFA) for any interactive access
* 	Just-in-time access — All access through break-glass mechanisms must be granted temporarily and must be revoked after a pre-define amount of time or when the emergency is declared as over
* 	Approval process — Access through a break-glass mechanism should be manually approved
* 	Auditing — All access through break-glass mechanisms must be audited and kept as evidence for further investigation
* 	Documented process — Organizations must have a documented and tested process for requesting, approving, using, and revoking break-glass accounts

Kubernetes Certificate Authority:
In Kubernetes, a Certificate Authority (CA) is an entity that issues digital certificates. Digital certificates are used to create secure connections between services within a Kubernetes cluster and to 
clients accessing those services. The CA is responsible for signing these certificates, which means it verifies the identity of the entity requesting the certificate and vouches for that entity's identity.
Kubernetes provides a certificates.k8s.io API, which allows you to manage TLS certificates in your cluster. This API lets you provision TLS certificates signed by a CA that you control, thereby establishing 
trust between various components of your Kubernetes system, such as services, pods, and nodes.

Here are some key points about Kubernetes CAs:
* Creating a CA: You can create a CA by generating a signing certificate. Tools like cfssl can be used to generate the CA key and certificate files (ca-key.pem and ca.pem)
* Using the CA: The CA is used to issue certificates that are used for various purposes, such as securing communication between Kubernetes components, authenticating clients, and issuing certificates 
for service accounts.
* Certificate Files: In a typical Kubernetes setup, the CA certificate (ca.pem) and the private key (ca.key) are stored in the "/etc/kubernetes/ca/" directory. These files are used by various components 
to validate and sign certificates 
* Certificate Signing Requests (CSR): To issue a certificate, a Certificate Signing Request (CSR) is created. The CSR is a block of encoded text that is given to the CA, who uses it to create a certificate 
for the requester. In Kubernetes, you can create a CSR and approve it to get a certificate
* Automating Certificate Management: Kubernetes provides mechanisms to automate the management of certificates using its API. This includes the ability to create, approve, and manage CSRs programmatically

kafka polling => Polling involves making repeated requests to a server to check for updates. However, traditional polling can be inefficient and “chatty,” leading to increased bandwidth usage. This is where long polling comes into play. Instead of the server immediately responding with a “not ready” message, it delays the response, allowing the client to check back later.
In Kafka, long polling is instrumental for clients subscribing to topics. The consumer sends a request to check for messages in a topic, and if none are found, Kafka holds the response until new messages arrive. This ensures that clients receive updates without continuously polling the server.1

what is a password or secret rotation?

Password or secret rotation refers to the practice of periodically changing passwords, API keys, encryption keys, or other types of secrets used to access systems, applications, or data. This practice is a critical component of security management and helps to mitigate the risk of unauthorized access due to compromised credentials. Here are some key aspects of password or secret rotation:

Why Rotate Passwords or Secrets?
Mitigate Risk of Compromise: If a password or secret is compromised, rotating it limits the window of opportunity for an attacker to use it.
Compliance: Many regulatory standards and security frameworks (e.g., PCI-DSS, HIPAA) require regular rotation of passwords and secrets.
Reduce Impact of Insider Threats: Regular rotation can help minimize the risk posed by disgruntled employees or other insiders who might misuse their access.
Limit Exposure: In case of a data breach, rotating secrets can help ensure that any exposed credentials are no longer valid.

Types of Secrets to Rotate
User Passwords: Passwords used by individuals to access systems and applications.
API Keys: Keys used to authenticate and authorize API requests.
Encryption Keys: Keys used to encrypt and decrypt data.
Database Credentials: Usernames and passwords used to access databases.
Service Account Credentials: Credentials used by applications or services to interact with other systems.

Best Practices for Secret Rotation
Automate Rotation: Use tools and scripts to automate the rotation process to reduce human error and ensure consistency.
Use a Secret Management System: Tools like HashiCorp Vault, AWS Secrets Manager, and Azure Key Vault can help manage and rotate secrets securely.
Set Rotation Policies: Define policies that specify how often secrets should be rotated (e.g., every 30, 60, or 90 days).
Monitor and Audit: Keep logs of secret rotations and monitor for any unauthorized access attempts.
Notify Stakeholders: Ensure that all relevant stakeholders are informed about the rotation schedule and any changes to secrets.
Test Rotations: Regularly test the rotation process to ensure that it works as expected and does not disrupt operations.

Challenges and Considerations
Downtime: Ensure that the rotation process does not cause downtime or disrupt services.
Backward Compatibility: Make sure that all systems and applications that rely on the secret are updated to use the new secret.
Security: Ensure that the rotation process itself is secure and does not expose the new secrets.

Example Tools for Secret Rotation
HashiCorp Vault: Provides dynamic secrets, automatic rotation, and secure storage.
AWS Secrets Manager: Automates the rotation of secrets and integrates with AWS services.
Azure Key Vault: Manages and rotates secrets, keys, and certificates in Azure.

In summary, password or secret rotation is a crucial security practice that helps protect systems and data from unauthorized access. By regularly changing credentials and using automated tools, organizations can significantly reduce the risk of security breaches.

what are gRPC and RPC connections?

RPC (Remote Procedure Call) and gRPC (gRPC Remote Procedure Call) are both protocols used for communication between different systems, typically over a network. They allow a program to execute a procedure (subroutine) on a different address space (commonly on another physical machine) as if it were a local procedure call.

RPC (Remote Procedure Call)

RPC is a protocol that one program can use to request a service from a program located on another computer in a network. It abstracts the details of the network communication, making it easier for developers to write distributed applications. The key features of RPC include:

Transparency: The client calls a remote procedure as if it were a local one, without needing to handle the details of the network communication.
Simplicity: It simplifies the process of writing distributed applications by hiding the complexity of the network communication.
Language Agnostic: RPC can be implemented in various programming languages.
However, traditional RPC has some limitations, such as lack of support for modern data formats and protocols, and it can be less efficient in terms of performance and scalability.

gRPC (gRPC Remote Procedure Call)

gRPC is a modern, open-source RPC framework developed by Google. It uses HTTP/2 for transport, Protocol Buffers (protobuf) as the interface description language, and provides features such as authentication, load balancing, and more. Key features of gRPC include:

HTTP/2: gRPC uses HTTP/2, which provides several advantages over HTTP/1.1, including multiplexing, flow control, header compression, and more efficient use of network resources.

Protocol Buffers: gRPC uses Protocol Buffers (protobuf) for serializing structured data, which is more efficient and faster than traditional text-based formats like JSON or XML.

Cross-Platform: gRPC supports multiple programming languages, making it easier to develop cross-platform applications.

Streaming: gRPC supports streaming requests and responses, allowing for more complex communication patterns like bidirectional streaming.

Performance: gRPC is designed for high performance, with low latency and high throughput.

Comparison
Transport Protocol: RPC can use various transport protocols (e.g., TCP, HTTP), while gRPC specifically uses HTTP/2.
Data Serialization: Traditional RPC might use different serialization formats (e.g., JSON, XML), whereas gRPC uses Protocol Buffers.
Performance: gRPC generally offers better performance due to its use of HTTP/2 and Protocol Buffers.
Features: gRPC provides additional features like streaming, built-in authentication, and load balancing, which are not typically part of traditional RPC implementations.

In summary, while both RPC and gRPC serve the same fundamental purpose of enabling remote procedure calls, gRPC offers a more modern, efficient, and feature-rich approach, making it a popular choice for building scalable and high-performance distributed systems.

explain to me how DLQ monitoing works?

DLQ (Dead Letter Queue) monitoring is a process used to track and manage messages that cannot be processed successfully by a message queue system. Here's how it generally works:

Dead Letter Queue (DLQ) Setup:

A DLQ is a special queue where messages that fail to be processed are sent. This can happen due to various reasons such as message format errors, processing logic failures, or timeouts.
Message Routing:

When a message cannot be processed by the main queue, it is automatically routed to the DLQ. This ensures that problematic messages do not block the processing of other messages.
Monitoring Tools:

Monitoring tools or dashboards are set up to keep track of the DLQ. These tools can provide insights into the number of messages in the DLQ, the reasons for failure, and the time messages have been in the queue.
Alerting:

Alerts can be configured to notify administrators or developers when the number of messages in the DLQ exceeds a certain threshold. This helps in quickly identifying and addressing issues.
Analysis and Troubleshooting:

Messages in the DLQ are analyzed to determine the cause of failure. This can involve checking message content, reviewing logs, and debugging the processing logic.
Reprocessing:

Once the issue is identified and resolved, messages can be reprocessed. This might involve moving them back to the main queue or directly processing them from the DLQ.
Reporting:

Regular reports can be generated to provide insights into the frequency and types of errors occurring, helping to improve the overall system reliability.
By effectively monitoring the DLQ, organizations can ensure that message processing systems are robust, reliable, and capable of handling errors gracefully.

** postgres table vaccuming **

In PostgreSQL, table vacuuming is a maintenance operation that helps manage storage and improve database performance. The process involves cleaning up dead tuples (obsolete rows) that result from updates and deletes.

1. MVCC (Multi-Version Concurrency Control): PostgreSQL uses MVCC to handle concurrent transactions. When a row is updated or deleted, the old version of the row is not immediately removed. Instead, a new version of the row is created, and the old version is marked as obsolete or "dead." This allows other transactions to continue accessing the old version until they are completed.
2. Dead Tuples: Over time, as updates and deletes occur, the number of dead tuples in a table can increase. These dead tuples consume storage space and can lead to inefficient use of resources, as they still need to be scanned during certain operations.
3. Vacuuming: The VACUUM command is used to reclaim storage occupied by dead tuples. It marks the space occupied by these tuples as available for future use, effectively cleaning up the table. Vacuuming also helps update the visibility map, which can improve the efficiency of index-only scans.

Regular vacuuming is essential for maintaining the health and performance of a PostgreSQL database, especially in environments with frequent updates and deletes.

# basic vaccum
VACUUM;

# Vacuum a Specific Table
VACUUM my_table;

# vaccum with analyze => ANALYZE option updates the statistics used by the PostgreSQL query planner, which can help improve query performance. This command vacuums and analyzes a specific table
VACUUM ANALYZE my_table;

# vaccum full => The FULL option reclaims more space by compacting the table, but it requires an exclusive lock on the table. Use this option with caution, as it can impact performance
VACUUM FULL my_table;

When an Aurora cluster is created, encryption must be enabled whilst using a customer-managed key (CMK).

DLQs
Welcome to the DLQ documentation.

Overview
What are DLQs?
Dead Letter Queues (DLQs) are a standard error handling mechanism for streaming software systems. In certain scenarios messages that cannot be processed by a production component when read from a queue are instead placed on a separate queue, the DLQ, for manual investigation and recovery. This ensures that subsequent messages on the original queue can continue to be processed, while any messages that cannot be processed are retained in full, i.e. there is no data loss.

Once a message has been placed on a DLQ this indicates that the standard processing of the message was not able to complete, and no further processing of the message will occur automatically. You must take additional steps in order to recover the original operation that was unable to complete. Failure to do so can lead to incomplete Vault functionality.

When are DLQs used?
The errors encountered by a Vault component when processing a message consumed from a Kafka topic fall into two broad categories:

Transient Errors occur when automatically retrying at a later time, without any state change within Vault, is likely to lead to successful processing of the message. For example if the database is temporarily unavailable, this would be a retryable error as when the database becomes available again the message will be processed successfully.

Non-Transient Errors occur when automatically retrying, without any state change within Vault, is unlikely to lead to successfully processing the message. For example, if the message cannot be deserialised by the consumer, attempts to retry processing will not be successful.

While most transient errors are handled within Vault, DLQs are used as a recovery mechanism for Kafka messages that are unable to be processed due to some non-transient errors.

The Vault DLQ process is as follows:

A Vault component which is a consumer of a particular Kafka topic consumes a message from the topic and attempts to process it.

While processing the message, a non-transient error is encountered, meaning retrying with the system in its current state will not produce a successful outcome.

The message is placed on a dedicated DLQ Kafka topic. Processing of subsequent messages from the original topic continues, but processing of the message that has been placed on the DLQ does not continue.

Note that in some cases when a transient error is encountered when processing a message, depending on the cause of the error, processing of the message may be retried indefinitely. For example if the database remains unavailable. Cases like this should still be monitored as they may still require manual intervention to proceed (e.g. ensuring services can communicate with one another).

DLQs may contain PII data both in the message bodies and the error output. As a result any personnel or system reading data from any DLQ may be exposed to it. You must take the appropriate steps to ensure that readers of DLQ messages have the appropriate authorisation.

DLQ naming
All DLQ topics within Vault follow a standard naming convention of containing .dlq or .failure in the topic name, most often at the end.

DLQ message format
When a message is placed on a DLQ topic, the format of the message on the DLQ will be as follows:

The body of the message is identical to the original message, in the same format (JSON or Protobuf). For example if the originally consumed message is an AccountEvent, then the DLQ’d message body will be the same AccountEvent message.

DLQ metadata detailing information about the original message is present in the x-tm-dlq-metadata message header in the form of a standard DLQ metadata message (see below for the full format). DLQ metadata values will always be formatted as JSON key / value pairs.

Generally the processing error that led to the message being DLQ’d is present in either the x-tm-vault-error message header or in the stack_trace header within the DLQ metadata . These values will always be formatted as a JSON key / value pair.

The DLQ metadata contains four mandatory fields and one optional field all as JSON key / value pairs:

original_headers. This is a repeated field containing all the Kafka headers present in the original message.

original_topic. This is a single string whose value is the topic that the original message was consumed from.

original_consumer_group. This is a single string whose value is the consumer group used by the consumer which encountered the error while processing the message.

original_timestamp. This is a single string whose value is the timestamp of when the original message was created.

stack_trace. This is an optional single string field which, if present, will contain the processing error.

Monitoring DLQs
As mentioned above, you must actively monitor DLQs for new messages. In many cases, a message being placed on a DLQ represents a critical processing error which requires immediate attention.

Thought Machine provides Prometheus Alerts that track new messages being placed onto DLQ topics. Alert pagers should be built on top of these alerts to inform you of new messages placed on a DLQ.

For more information on how to configure Alert Pagers, as well as the full list of DLQ alerts, see the Observability Stack Installation and User guide.

Detailed information about each individual DLQ can be found under the associated API section. This includes the processing being performed, the impact of a message being placed on that DLQ, and potential recovery steps to follow.

DLQ recovery
Any time a message is placed on a DLQ, you must take any necessary action to recover processing. Failure to do so will result in a loss of data and/or Vault functionality. While the severity of the functionality affected by a message placed on a DLQ will vary, note that even for less critical issues you must recover from DLQ messages within the timeframe of your Kafka retention period, which defaults to 7 days. Failure to do so will result in the message on the DLQ being permanently deleted, meaning recovery of the data/functionality may no longer be possible.

When a message is detected on a DLQ Kafka topic:

Consume the message from the DLQ, including the headers. As mentioned above the headers contain the error message. If displaying the Kafka message in full, take care to ensure viewers have the appropriate authorisation to view the data.

Consult the DLQ documentation for the affected component in the corresponding API section of the Documentation Hub. If the relevant documentation does not provide sufficient information for the DLQ in question, contact Thought Machine support, following the process in your Service Procedure Manual.

If the specific error is documented for the affected DLQ, follow the recovery instructions.

If the error is not documented for the affected DLQ, contact Thought Machine support, following the process in your Service Procedure Manual.

You should only manually interact with DLQ Kafka topics in error scenarios, and when doing so must take care not to use any consumer groups that are used by any production services

Reading messages from a DLQ
How you interact with Kafka topics within Vault will depend on your Kafka hosting solution and internal processes. If a lightweight approach is required for consuming messages, Thought Machine recommends the use of Kafkacat for interacting with Vault DLQ Kafka topics in error scenarios. Instructions for how to download and use Kafkacat can be found here, while providing the -h option when running Kafkacat will provide more information about the available functionality. Remember that wherever you choose to run Kafkacat, it will need access to your Kafka broker.

If you are using Kafkacat to consume and read messages from a DLQ, we recommend:

Running via Docker to ensure the latest version of Kafkacat is used. The command should start with docker run --rm confluentinc/cp-kafkacat kafkacat -b <your_kafka_broker> -t <name_of_dlq_topic> -C.

Using the -J option to ensure the headers are displayed along with the message body for the consumed messages. Alternatively you can specify a format via -f which must include the %h header token.

If you wish to only see the headers, you can provide a format that only contains the header token, e.g. -f ‘Headers: <%h>’. This may be useful if the original message contains data the user is not authorised to see (note however that PII data can sometimes occur in the error message, which will always be present in the headers). For a full list of all the format tokens and what data will be displayed, you can run docker run --rm confluentinc/cp-kafkacat kafkacat -h and consult the ‘Format string tokens:’ section. Only the data associated with a given token will be displayed when the -f option is used.

Kafkacat will produce output to Stdout by default.

If the message body is in protobuf format, it will not be human readable when read from the DLQ. You are still required to deserialise using the provided Vault .proto files. See the Deserialising Proto Messages section below. If the DLQ in question does not have the message type documented, contact Thought Machine support, following the process in your Service Procedure Manual.

If your Kafka solution or internal process prohibits the use of Kafkacat, you must implement your own method of consuming from/producing to Vault DLQ Kafka topics.

Deserialising Protobuf messages
Depending on your environment settings, some DLQ message bodies will be in either Protobuf or JSON format:

If the format is JSON, you do not need to follow the remainder of this section and must not use protoc on your message output.

If the format is Protobuf, you will need to deserialise the message before it is human readable, instructions for which are below.

To deserialise an encoded protobuf message, you must have access to the corresponding .proto file that contains the message definition in question. Many of these .proto files can be found in the 'Downloading the proto files' part of the Streaming API documentation for the relevant API. Once you have this file you can convert the message into human readable JSON. If you do not have access to the corresponding .proto file, please contact Thought Machine support, following the process in your Service Procedure Manual.

To determine the correct .proto file for deserialising the body of a DLQ:

Go to the documentation for the specific DLQ in question.

Find the message type under the 'What message has been sent to the DLQ?' section.

Find the .proto file that contains this message type. There will be a Message <value> line in the file, where <value> is the message type from the previous step.

There are many ways that a .proto file can be used to read a message in protobuf format. If a lightweight approach is needed, Thought Machine recommends the use of Protoc.

Protoc can be run on any protobuf bytes to convert to JSON as follows:protoc --decode=<package_name.message_name> <path_proto_file>

The package name is defined in the .proto file by the line: package <package_name>;

For example:

protoc --decode=test_package.TestMessage path_to_proto/test.proto

would deserialise protobuf bytes into JSON format for a protobuf message of type TestMessage where:

The TestMessage type is defined in 'test.proto'.

The 'test.proto' contains a package test_package; line, which defines the package name.

The 'test.proto' file is located in your /path_to_proto/ directory.

If using protoc in conjunction with Kafkacat, you should only read the message body from Kafka before passing it to protoc. For example: docker run --rm confluentinc/cp-kafkacat kafkacat -b <your_kafka_broker> -t <name_of_dlq_topic> -C -D “” | protoc --decode=test_package.TestMessage path_to_proto/test.proto.

This article describes the steps you need to take to enable SSL for Kafka clients. This is written to be implemented in Spring microservices, but could also serve as a guide for other Kafka related applications.

Our Kafka clusters use mTLS, that means that both the server and the client hold a certificate that is signed by the Certificate Authority (CA). On establishing the connection, both the broker checks the client certificate, and the client checks the broker certificate. The checking is done by checking whether the certificate is signed by a CA that we have in the trust store. On the client side, we also check that the bootstrap server address is in the SAN part of the certificate.



So, to enable mTLS on the client side you need two pieces:

certificates
application configuration (usually in application.yaml for Spring Boot apps)


Known limitations
IMPORTANT

cert-manager has a hard limit on the CN length. Therefore, the total length of deployment name + namespace name cannot exceed 63 characters.
We have a kyverno policy which will prevent any deployments which violate this rule.
Enable mTLS for new Kafka or Cockroach client app
To enable new certificates, we need to add the next annotations to your Deployment/StatefulSet/Job:

metadata:
  name: test-service
  namespace: test
  annotations:
    dynamo.certificate.tls/active: "false"  # this annotation will disable old PCA webhook
    dynamo.certificate.cdb/client: "false"  # this annotation will disable old PCA webhook for CDB
    pca.icb.tls/active: "true"              # this annotation will enable new PCA webhook
Certificates will be generated automatically for K8S Deployments, StatefulSets and Jobs and will be mounted into each pod by mutating web hook.

Certificates will be located inside /certs/ subfolder inside each container within the pod.

List of available certificates/keys:

$ ls /certs/
ca.crt  key.der  keystore.jks  keystore.p12  tls.crt  tls.key  truststore.jks  truststore.p12
So, all we need to do is to configure an application to use them

In your application.yaml file, use the following parameters:

Which user principal is used by Kafka clients (consumers/producers)
The user principal, used for Kafka authorization, is derived from the certificate common name (CN) based on core-kafka SSL mapping rules.

For example:

CN from the certificate, which can be viewed by logging into the service container in the pod.

$ openssl x509 -in /certs/tls.crt -text | grep "CN ="
        Issuer: C = US, O = JPMC, OU = Dynamo, ST = New York, CN = dynamo.dev.eu-west-1.aws.jpmchase.net, L = New York
        Subject: CN = movemoney-stip-balance-updater-service.svc.cluster.local
The CN is then given to the SSL mapping rule RULE:^CN=([a-zA-Z0-9\\-_]*)\\..*/$1/  which captures the principal name as movemoney-stip-balance-updater-service in the above example.

What if you use jobs with auto-generated suffix
If you create a job with a randomly generated suffix, the CN for it will also contain that suffix.

Because of that, user principle won't match with the ACL rule, and your pod will not be able to communicate with the topic. You may find more details about it here.

To fix that, we will need to apply additional SSL mapping rules which require brokers to restart. Therefore, you need to create a support ticket to the CPE Platform team and request this change.

Please create a support ticket using go/coredsd or go/cpedsd

Certificates rotation
cert-manager is capable to update certificates automatically. Once certificate reaches renewal date, cert-manager will automatically issue a new certificate and push the changes to the kubernetes secrets. By default, certificate age is configured to 365 days, and certificate will be renewed when it is 270 days old. There is a feature request to configure certificate age through the annotations ( DYN-495655 - certificate duration from annotations To Do )



To be able to use new certificate, you need to restart the pods for your Deployment/StatefulSet/Job.

NOTE: in legacy PCA implementation, you had to trigger the updates for Deployments, StatefulSets or Jobs to get a new certificate (normally, by adding a new label). Now, it is not required.


We recommend terminating your program with system exit code 1 in case of SSL handshake issue so that the pod will be restarted automatically by Kubernetes in case of certificate expiration

Old PCA implementation was issuing and injecting certificates for all Deployments, StatefulSets and Jobs by default no matter you use them or not.

New PCA implementation, in contrary, enables the certificates injection only when you specified required annotation (as mentioned in sections above)

If your application does not need any certificates (for Kafka or CDB), you should explicitly disable them.

To do that, simply add the next annotations:

metadata:
  name: test-service
  namespace: test

    dynamo.certificate.cdb/client: "false"  # this annotation will disable old PCA webhook for CDB
    pca.icb.tls/active: "false"             # this annotation will disable new PCA webhook
Alternatively, add label pca.icb.gencert/webhook: "ignore" to the namespace where your resource is located, in this case new PCA webhook will ignore all resources in this namespace.

So you want to create or update a Cockroach database
CRDs
Cockroach Database
Cockroach Database
apiVersion: dynamo.jpmorgan.com/v1 # Do not change
kind: CockroachDatabase # Do not change
metadata:
  namespace: 105250-namespace # change to your namespace
  name: my-database
Names within the CRD must only contain alphanumeric characters and "-" (the "-" will be converted to "_" in the controller) but cannot end or start with "-" and can have up to 63 characters, otherwise the CRD will fail.
Applying a CockroachDatabase as above will do the following:

create a database called: 'my_database'
create a read-write user called: 'my_database' with the following database privilege: SELECT, INSERT, UPDATE, DELETE  
create a 'Liquibase' user called: 'my_database_cj' with the following database grants: CREATE, DROP and  privilege of  SELECT, INSERT, UPDATE, DELETE
Cockroach Database Grant
Cockroach Database
apiVersion: dynamo.jpmorgan.com/v1 # Do not change
kind: CockroachGrant # Do not change
metadata:
  namespace: 105250-namespace # change to your namespace
  name: my-extra-grant
spec:
  user: my-outbox-deployment # if user doesn't exist, the grant will fail
  database: my-database # database name should use dashes instead of underscores else the grant will fail
  databaseGrants: [CREATE, DROP, SELECT, INSERT, UPDATE, DELETE ] # optional grants to grant on a database level, field can be omitted if not needed
  tableGrants:
    - table: my-outbox
      action: [ SELECT, UPDATE ] # CREATE, DROP, ETC.
The default applicable grants are: CREATE, DELETE, DROP, GRANT, INSERT, SELECT, UPDATE (anything other than the grants of the admin user create_cockroach_database will fail).

The database and its associated grant CRDs must be in the same namespace, otherwise the CRD will fail.
Names within the CRD can only contain alphanumeric characters and "-" (the "-" will be converted to "_" in the controller) but cannot end or start with "-" and can have up to 63 characters, otherwise the CRD will fail.
Database grants are applied on the whole database, including existing tables.
The user to which the grant CRD is applied has to exist already, otherwise the CRD will fail.
The database to which the grant is applied must already have a CockroachDatabase CRD created, otherwise the CRD will fail.
Note the jdbc url used in the CRD is: 

jdbc:postgresql://cockroach-public:26257/defaultdb?sslmode=verify-full&sslrootcert=/cdb/client/ca.crt&sslcert=/cdb/client/client.create_cockroach_database.crt&sslkey=/cdb/client.key.pk8&ApplicationName=create-cockroach-database
How to migrate from cockroach_sql_runner to CRD
Teams can migrate at any time. At the moment both the cockroach_sql_runner and the CRD are supported, but the former will be disabled in the future.

How to deploy
You deploy the CRDs along with your existing helm (either as a separate yaml or a new helm project) into the spoke cluster that you run from and it will be recognized and picked up by the Cockroach Controller. So if you have your microservice deployed in DCORE, you would deploy the CockroachDatabse CRD in the same namespace. You can choose to do this at the same time as the microservice, or as part of a different helm project and deploy ahead of time. Any calls to the corresponding cockroach_sql_runner script(s) will have to be removed from the spinnaker pipeline definitions (i.e. from the dinghyfiles).

Here is some sample code for migrating database creation: core-psd2-tpp-authoriser-service

Note that if you have liquibase jobs in your pipeline, they will have to be applied after helm is applied.

add grants	can add multiple grants on multiple tables within a database at a time	can add select and update on one table within a database at a time

FAQ
Can I delete a database?
You can delete the CRD resources, but it will not remove the grants/databases at this moment in time. If you need to delete a database, you can leverage the existing pipelines.
Are there any controls around who can create a database where?
At the moment we don't have any controls/restrictions in place. The future idea is that the create_cockroach_database user is only accessible to this CRD controller.
How do I know my database is created?
Our controller updates the CRD with a status stanza that will indicate the current state.
Do I have to migrate?
At this stage both solutions will work and can be used at the same time. Actions are only done in an additive fashion and are effectively idempotent.
How do I add permissions when I add tables?
The default rule in Cockroach is that when a table is created, it inherits the permissions from the database. That is why when we create the database, we grant appropriate permissions for the default users.

I. Introduction
Objective

This document details the Minimum Acceptance Criteria to ensure adequate and detailed documentation is included in ServiceNow Change Records.

Scope

This criteria is valid for all Normal Change Records

Roles and Responsibilities

The Change Owner is responsible for populating the CHG records with the relevant data.

The Change Approver is responsible for ensuring the MAC is met before approving the Change.

II. Main Details Section
Configuration Item

Input in the Configuration Item that is being impacted by the change.
Short Description

MUST - Provide a high-level overview / description of the change in business language (limit technical jargon).
MUST - use business language and avoid acronyms.
SHOULD - Prefix with the application name.
DON'T - just add a link to another site/ ticket.
Description

MUST - Clearly state what the change is going to do and why it is required.
MUST - Use business language and explain acronyms.
MUST - Summarize the risks of implementing the change (i.e. what could go wrong and what is the likelihood?) and/or business impact of NOT implementing it.
MUST - Explain the business driver/rationale/requirement for the change and document the business impact of NOT implementing the change.
MUST - Provide a description of all changes to be implemented.
MUST – Include all DYN tickets associated to the change
SHOULD - List any EPV (privileged access) accounts that are required to implement the change.
If the change window is more than 24 hours, add a justification for the extended change window.
Change Window – Planned Start / End Dates

Change Window = Implementation + Technical Validation + Back Out Plan + Technical Validation of the Backout
MUST - Include Breakglass Operations.
MUST - factor in any dependencies, e.g. resource availability, batch cycle completion, systems availability.
While firmwide recommends that changes do not exceed 24 hours, ensure change window is sufficiently long.
If the change window is more than 24 hours, the implementation plan must contain sufficient details (day-by-day breakdown of activities) to justify the change window.
Risk

The Risk Level is automatically calculated in ServiceNow using the Risk Model and is fully data driven.
The Change Owner can manually raise the Risk Level if necessary.
III. Planning Section
Release Attestation

Declare if the change is based on a software release or code update and as such is subject to all applicable controls for Technology Development (TCS-071/TCS-074).
Fallback Strategy

Select from the Drop Down if the Fallback Strategy is Backout or Fix Forward.
The fix forward solution is to stabilize the environment. Justification is required if Fix Forward is selected.
Pre-implementation plan

MUST - Document activities that were completed prior to the change implementation to ensure success.
MUST - Utilize JET evidence store (go/JET). Otherwise, pre-Implementation testing evidence should be attached to the Change Record.
SHOULD - If applicable, mention previous, similar, successful implementations from the past.
Implementation Plan

MUST - Clearly document the steps of the implementation plan, including critical milestones and the teams responsible for performing them.
MUST – Detail all the different test types of test including smoke, alpha with associated JET IDs.
MUST – Detail the list of tests and their pass criteria as a %.
MUST – For any tests that did not pass ICB quality gates, a decision ticket must be included to show evidence of risk acceptance of the failed tests.
MUST – Explicitly document which controls and not for the release (to ensure that change approvers are informed of the necessary control requirements).
SHOULD - Include a detailed technical plan which is attached to the Change record or Implementation Task record.
SHOULD - Identify a ‘point of no return’ in the implementation plan. Upon reaching this point, assess if the change implementation is at risk of going beyond the Planned End time.
Fallback Strategy Plan

MUST - State if the backout is automated or manual, and whether the backout plan has been tested/proven.
MUST - Include the contact details of the person responsible for executing the backout.
SHOULD - Include a detailed step by step plan which is attached to the Change Record.
Post Validation Plan

MUST - Describe the checks that can be feasibly conducted within the change window to validate the success of the change. (evidence of this is required for Post Change Validation)
MUST - Clearly state the success criteria and who is responsible for executing the checks.
IV. Other useful details
Outages

If the implementation will cause a planned outage or degradation of services, an Outage record must be created; if there are multiple outages they should be defined separately.
Change Task – Validation

Document post change validation testing and attach relevant evidence to the ServiceNow Change Record as documented in the Post Validation Plan.
 Steps to create a Change Task - Validation
V. Key Takeaways
Change data should be clear and simple to understand – limit the use of technical jargon and don’t use acronyms.
Include details of ALL changes that are included in the release.
Be generous when planning the change window.
Include a detailed summary of context if adding dynamic links to Change Records
Why? – Firmwide guidance is to avoid dynamic links that are not accessible to all reviewers and auditors
Use Jet Evidence Store for evidence as applicable (attach evidence to the Change Record)
Ensure you are thorough in your pre-implementation, implementation, fall-back strategy and post validation test plans. (use tool tip links in SNOW if in doubt)
Refer to the Change Quality Review Playbook for examples of good vs bad changes
