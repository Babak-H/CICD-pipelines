HashiCorp Vault Grafana Metrics
Created by Babak Habibnejad Gohardani on Sep 25, 2024
Health Status: group by (pod) (up{job="hault"})  => checks if the hault pods are up and working or not (currently only shows existing pods)

Sealed Status: max(1 + vault_core_unsealed{}) => if the vault is unseal (unlocked) value is 2 otherwise 1 (sealed)

Secrets: vault_secret_kv_count => count of key-value (KV) secrets stored in HashiCorp Vault visible in column Number of entries, rest is info about the mount path of secrets and the app that contains the secret,...

Number of Operations in secret: vault_route_read_secret__count =>  the count of read operations on secrets through specific routes in Vault. In Vault, routes are used to define how requests are handled, and this metric would track the number of times secrets are read via these route

Time of Operations in secret: avg(rate(vault_route_read_${mountpoint}__sum[1m]) / rate(vault_route_read_${mountpoint}__count[1m]) * 1000) => how long each reading or listing of secrets takes in this namespace, by average

Heap objects used: avg(vault_runtime_heap_objects{} / vault_runtime_malloc_count{}) => (number of heap objects currently allocated in the memory of the Vault process. Heap objects are dynamically allocated memory blocks) / ( total number of memory allocation (malloc) operations performed by the Vault process),  average number of heap objects per memory allocation operation, lower than 0.2 means memory is being used efficiently 

Allocated MB: avg(vault_runtime_alloc_bytes{}/1000000) =>  number of Megabytes of memory currently allocated and in use by the Vault process, we can view how the memory usage is on average for all 3 Vault pods

Available Tokens: avg(vault_token_count) => number of active tokens in HashiCorp Vault. In Vault, tokens are used for authentication and authorization. They are issued to clients and can have various properties such as time-to-live (TTL), policies, and renewable status

Pending Tokens: avg(vault_token_create_count - vault_token_store_count) => count of token creation operations in HashiCorp Vault - count of tokens currently stored in Vault , so you will get how many tokens are created but not saved in Vault

Request Handling: sum(vault_core_handle_request) by (quantile) => which quantile (p 0.5 , p 0.9 , p 0.99) handles how many requests

Log Requests: vault_audit_log_request_count, vault_audit_log_response_count => count of audit log requests in Vault. Vault's audit logging feature records all requests and responses to the Vault server, providing a detailed log of all operations for security and compliance purposes. This metric would track the number of audit log entries created

Log Request/Response Failures: vault_audit_log_request_failure, vault_audit_log_response_failure => count of failed attempts to log request/responses in the audit log of Vault. Vault's audit logging feature records all requests and responses to the Vault server, and this metric would track the number of times an attempt to log a request/response has failed. Failures could occur due to various reasons such as misconfigurations, permission issues, or storage problems.

This article describes the steps you need to take to enable SSL for Kafka clients. This is written to be implemented in Spring microservices, but could also serve as a guide for other Kafka related applications.

Our Kafka clusters use mTLS, that means that both the server and the client hold a certificate that is signed by the Certificate Authority (CA). On establishing the connection, both the broker checks the client certificate, and the client checks the broker certificate. The checking is done by checking whether the certificate is signed by a CA that we have in the trust store. On the client side, we also check that the bootstrap server address is in the SAN part of the certificate.



So, to enable mTLS on the client side you need two pieces:

certificates
application configuration (usually in application.yaml for Spring Boot apps)


Known limitations
IMPORTANT

cert-manager has a hard limit on the CN length. Therefore, the total length of deployment name + namespace name cannot exceed 63 characters.
We have a kyverno policy which will prevent any deployments which violate this rule.
Enable mTLS for new Kafka or Cockroach client app
To enable new certificates, we need to add the next annotations to your Deployment/StatefulSet/Job:

metadata:
  name: test-service
  namespace: test
  annotations:
    dynamo.certificate.tls/active: "false"  # this annotation will disable old PCA webhook
    dynamo.certificate.cdb/client: "false"  # this annotation will disable old PCA webhook for CDB
    pca.icb.tls/active: "true"              # this annotation will enable new PCA webhook
Certificates will be generated automatically for K8S Deployments, StatefulSets and Jobs and will be mounted into each pod by mutating web hook.

Certificates will be located inside /certs/ subfolder inside each container within the pod.

List of available certificates/keys:

$ ls /certs/
ca.crt  key.der  keystore.jks  keystore.p12  tls.crt  tls.key  truststore.jks  truststore.p12
So, all we need to do is to configure an application to use them

In your application.yaml file, use the following parameters:

spring:
  kafka:
    bootstrap-servers: ${KAFKA_BOOTSTRAP_SERVERS:core-kafka.105250-kafka.svc.cluster.local:9092}
    ssl:
      key-store-location: file:///certs/keystore.p12
      key-store-password: ${CERT_KEY_STORE_PASSWORD}
      key-store-type: PKCS12
      trust-store-location: file:///certs/truststore.p12
      trust-store-password: ${CERT_KEY_STORE_PASSWORD}
    producer:
      value-serializer: io.confluent.kafka.serializers.KafkaAvroSerializer
    properties:
      schema.registry.url: ${SCHEMA_REGISTRY_URL:https://core-schema-registry.105250-kafka.svc.cluster.local:8081}
      schema.registry.ssl.truststore.location: /certs/truststore.p12
      schema.registry.ssl.truststore.password: ${CERT_KEY_STORE_PASSWORD}
      schema.registry.ssl.keystore.location: /certs/keystore.p12
      schema.registry.ssl.keystore.password: ${CERT_KEY_STORE_PASSWORD}
      schema.registry.ssl.keystore.type: PKCS12
      security.protocol: SSL
      ssl.endpoint.identification.algorithm: ${KAFKA_HTTPS:https}


NOTE

We use the same password to encrypt the trust store and key store in p12 and jks formats.

That password is available as a CERT_KEY_STORE_PASSWORD environment variable and will be generated and injected into your pod automatically by mutating the webhook.

Which user principal is used by Kafka clients (consumers/producers)
The user principal, used for Kafka authorization, is derived from the certificate common name (CN) based on core-kafka SSL mapping rules.

For example:

CN from the certificate, which can be viewed by logging into the service container in the pod.

$ openssl x509 -in /certs/tls.crt -text | grep "CN ="
        Issuer: C = US, O = JPMC, OU = Dynamo, ST = New York, CN = dynamo.dev.eu-west-1.aws.jpmchase.net, L = New York
        Subject: CN = movemoney-stip-balance-updater-service.svc.cluster.local
The CN is then given to the SSL mapping rule RULE:^CN=([a-zA-Z0-9\\-_]*)\\..*/$1/  which captures the principal name as movemoney-stip-balance-updater-service in the above example.

What if you use jobs with auto-generated suffix
If you create a job with a randomly generated suffix, the CN for it will also contain that suffix.

Because of that, user principle won't match with the ACL rule, and your pod will not be able to communicate with the topic. You may find more details about it here.

To fix that, we will need to apply additional SSL mapping rules which require brokers to restart. Therefore, you need to create a support ticket to the CPE Platform team and request this change.

Please create a support ticket using go/coredsd or go/cpedsd

Certificates rotation
cert-manager is capable to update certificates automatically. Once certificate reaches renewal date, cert-manager will automatically issue a new certificate and push the changes to the kubernetes secrets. By default, certificate age is configured to 365 days, and certificate will be renewed when it is 270 days old. There is a feature request to configure certificate age through the annotations ( DYN-495655 - certificate duration from annotations To Do )



To be able to use new certificate, you need to restart the pods for your Deployment/StatefulSet/Job.

NOTE: in legacy PCA implementation, you had to trigger the updates for Deployments, StatefulSets or Jobs to get a new certificate (normally, by adding a new label). Now, it is not required.


We recommend terminating your program with system exit code 1 in case of SSL handshake issue so that the pod will be restarted automatically by Kubernetes in case of certificate expiration

What if I don't need certificates at all?
Old PCA implementation was issuing and injecting certificates for all Deployments, StatefulSets and Jobs by default no matter you use them or not.

New PCA implementation, in contrary, enables the certificates injection only when you specified required annotation (as mentioned in sections above)

If your application does not need any certificates (for Kafka or CDB), you should explicitly disable them.

To do that, simply add the next annotations:

metadata:
  name: test-service
  namespace: test
  annotations:
    dynamo.certificate.tls/active: "false"  # this annotation will disable old PCA webhook for Kafka
    dynamo.certificate.cdb/client: "false"  # this annotation will disable old PCA webhook for CDB
    pca.icb.tls/active: "false"             # this annotation will disable new PCA webhook
Alternatively, add label pca.icb.gencert/webhook: "ignore" to the namespace where your resource is located, in this case new PCA webhook will ignore all resources in this namespace.

So you want to create or update a Cockroach database
CRDs
Cockroach Database
Cockroach Database
apiVersion: dynamo.jpmorgan.com/v1 # Do not change
kind: CockroachDatabase # Do not change
metadata:
  namespace: 105250-namespace # change to your namespace
  name: my-database
Names within the CRD must only contain alphanumeric characters and "-" (the "-" will be converted to "_" in the controller) but cannot end or start with "-" and can have up to 63 characters, otherwise the CRD will fail.
Applying a CockroachDatabase as above will do the following:

create a database called: 'my_database'
create a read-write user called: 'my_database' with the following database privilege: SELECT, INSERT, UPDATE, DELETE  
create a 'Liquibase' user called: 'my_database_cj' with the following database grants: CREATE, DROP and  privilege of  SELECT, INSERT, UPDATE, DELETE
Cockroach Database Grant
Cockroach Database
apiVersion: dynamo.jpmorgan.com/v1 # Do not change
kind: CockroachGrant # Do not change
metadata:
  namespace: 105250-namespace # change to your namespace
  name: my-extra-grant
spec:
  user: my-outbox-deployment # if user doesn't exist, the grant will fail
  database: my-database # database name should use dashes instead of underscores else the grant will fail
  databaseGrants: [CREATE, DROP, SELECT, INSERT, UPDATE, DELETE ] # optional grants to grant on a database level, field can be omitted if not needed
  tableGrants:
    - table: my-outbox
      action: [ SELECT, UPDATE ] # CREATE, DROP, ETC.
The default applicable grants are: CREATE, DELETE, DROP, GRANT, INSERT, SELECT, UPDATE (anything other than the grants of the admin user create_cockroach_database will fail).

The database and its associated grant CRDs must be in the same namespace, otherwise the CRD will fail.
Names within the CRD can only contain alphanumeric characters and "-" (the "-" will be converted to "_" in the controller) but cannot end or start with "-" and can have up to 63 characters, otherwise the CRD will fail.
Database grants are applied on the whole database, including existing tables.
The user to which the grant CRD is applied has to exist already, otherwise the CRD will fail.
The database to which the grant is applied must already have a CockroachDatabase CRD created, otherwise the CRD will fail.
Note the jdbc url used in the CRD is: 

jdbc:postgresql://cockroach-public:26257/defaultdb?sslmode=verify-full&sslrootcert=/cdb/client/ca.crt&sslcert=/cdb/client/client.create_cockroach_database.crt&sslkey=/cdb/client.key.pk8&ApplicationName=create-cockroach-database
How to migrate from cockroach_sql_runner to CRD
Teams can migrate at any time. At the moment both the cockroach_sql_runner and the CRD are supported, but the former will be disabled in the future.

How to deploy
You deploy the CRDs along with your existing helm (either as a separate yaml or a new helm project) into the spoke cluster that you run from and it will be recognized and picked up by the Cockroach Controller. So if you have your microservice deployed in DCORE, you would deploy the CockroachDatabse CRD in the same namespace. You can choose to do this at the same time as the microservice, or as part of a different helm project and deploy ahead of time. Any calls to the corresponding cockroach_sql_runner script(s) will have to be removed from the spinnaker pipeline definitions (i.e. from the dinghyfiles).

Here is some sample code for migrating database creation: core-psd2-tpp-authoriser-service

Note that if you have liquibase jobs in your pipeline, they will have to be applied after helm is applied.

FAQ
Can I delete a database?
You can delete the CRD resources, but it will not remove the grants/databases at this moment in time. If you need to delete a database, you can leverage the existing pipelines.
Are there any controls around who can create a database where?
At the moment we don't have any controls/restrictions in place. The future idea is that the create_cockroach_database user is only accessible to this CRD controller.
How do I know my database is created?
Our controller updates the CRD with a status stanza that will indicate the current state.
Do I have to migrate?
At this stage both solutions will work and can be used at the same time. Actions are only done in an additive fashion and are effectively idempotent.
How do I add permissions when I add tables?
The default rule in Cockroach is that when a table is created, it inherits the permissions from the database. That is why when we create the database, we grant appropriate permissions for the default users.
